# Phase 0 Research: Delete Entity with Subtype Choice

## Existing state (from codebase survey)

- **No entity deletion exists today.** `src/commands/` only has creation (`addEntity.ts`). No `deleteEntity.ts`, no `ontograph.deleteEntity` command, no delete entry in `package.json`'s `contributes.menus`/`contributes.commands`.
- **Hierarchy is stored per-entity, not in a shared graph structure.** `OWLClass.superClassIris` (`src/model/OntologyModel.ts`) and `OWLProperty.superPropertyIris` (inherited by `OWLObjectProperty`/`OWLDataProperty`) hold each entity's *direct* declared parents. There is no reverse index (children-of-X) maintained on the model; each tree-view provider builds its own `childrenOf`/`parentsOf` maps by inverting these pointers at `buildIndex()` time (see `ClassHierarchyProvider.ts:31-87`, `ObjectPropertyProvider.ts:42-47`, `DataPropertyProvider.ts:41-46`).
- **A precedent for "direct subclass" computation already exists** in `cli/src/commands/core/entityInfoCommand.ts:205-221`. It accounts for plain `SubClassOf` declarations *and* named-conjunct membership inside `EquivalentClasses`/complex `SubClassOf` expressions (conjunction-elimination case — fixed recently per `cli-label-resolution`/`entity-info` history). This is the most correct existing definition of "direct subtype" in the codebase and should be reused/extracted rather than re-derived.
- **Sync-layer removal machinery already exists** for annotations (`AnnotationSync.ts`, `toRemove`/`toRemoveKeys` diffing) and axioms (`AxiomSync.ts`, `regRemoveChunkIdxs`/`gciRemoveAbsIdxs`), used today to reconcile in-place edits. Deleting an entity needs the same "remove all lines referencing IRI X" capability, generalized to a full-entity removal rather than a partial diff.
- **Reactive model cleanup precedent**: `src/sync/incrementalReload.ts:235-243` already deletes an entity's map entry (`model.classes`/`objectProperties`/etc.) when an external edit removes it from the reloaded text. The new delete command needs the equivalent forward operation (mutate the model directly instead of waiting for a reload) plus writing the corresponding source-file edit.
- **View refresh precedent**: `setRefreshAllViews` callback (introduced in `019-create-entity`) already lets a command trigger a full tree-view refresh after a model mutation — reusable as-is.

## Decisions

### D1: Where to compute "direct subtypes" for delete
- **Decision**: Extract the direct-subclass logic from `entityInfoCommand.ts` (SubClassOf + named-conjunct-in-EquivalentClasses/complex-SubClassOf cases) into a shared model-layer helper (e.g. `src/model/OntologyIndex.ts` or a new small module in `src/model/`), used by both the CLI command and the new delete command. For object/data/annotation properties, the equivalent is `superPropertyIris`-only (properties have no equivalent-class-style conjunction case) — mirrors the `childrenOf` inversion already done independently in `ObjectPropertyProvider.ts`, `DataPropertyProvider.ts`, and `AnnotationPropertyProvider.ts`.
- **Rationale**: Avoids a third divergent reimplementation of "who is a direct subclass of X" (tree views, CLI, and now delete would each have their own otherwise). Keeps delete's reparenting/cascade counts consistent with what `entity-info`/tree views already show the user.
- **Alternatives considered**: Re-derive subtypes ad hoc inside the delete command (rejected — duplicates recently-fixed conjunction-elimination logic and risks drifting out of sync); use the reasoner's inferred hierarchy instead of asserted (rejected — deletion must act on the *asserted* axioms actually present in the file, since that's what gets rewritten; inferred hierarchy is reasoner-derived and not always available without running classification).

### D2: Confirmation & mode-choice UI
- **Decision**: Use VS Code's native `window.showQuickPick`/`showWarningMessage`-style modal APIs for the mode choice + confirmation, invoked from a new `ontograph.deleteEntity` command wired into `view/item/context` menus for the Classes/Properties tree views (mirrors the existing `copyIri`/`openGraph` context menu pattern).
- **Rationale**: No new webview is needed; this matches the lightweight, native-VS-Code-UI pattern already used for command confirmations elsewhere in the extension, and keeps the feature's surface area small.
- **Alternatives considered**: A custom webview dialog (rejected — disproportionate for a single yes/no + mode choice); silently defaulting to one mode without confirmation (rejected — spec FR-007 requires explicit confirmation with an affected-count).

### D3: Reparenting mechanics
- **Decision**: Reparenting is a model + sync-layer mutation: for each direct subtype of the deleted entity, replace the deleted entity's IRI in that subtype's `superClassIris`/`superPropertyIris` with the deleted entity's own former super-IRIs (deduplicated; falls back to no explicit superclass, i.e. root level, if the deleted entity had none), then let `AxiomSync` rewrite the affected `SubClassOf`/`SubPropertyOf` axiom lines in place.
- **Rationale**: Reuses the existing axiom-sync rewrite path rather than a full re-serialization, consistent with the project's in-place sync philosophy (`AxiomSync.ts`, `AnnotationSync.ts`).
- **Alternatives considered**: Re-serializing the whole file via `FunctionalSerializer` after every delete (rejected — CLAUDE.md's architecture explicitly favors targeted in-place sync over full re-serialization for interactive edits).
- **Implementation note (post-hoc)**: What actually shipped reuses `computeUpdatedText` (`src/views/EntityEditorPanel.ts`), the same per-entity annotation+axiom resync the Entity Editor's save path already calls, rather than editing `AxiomSync.ts`/`AnnotationSync.ts` directly — clearing an entity's axiom/annotation-bearing fields and calling `computeUpdatedText` makes it regenerate zero lines, and the existing diff machinery removes the rest. `AxiomSync.ts`/`AnnotationSync.ts` themselves were not modified; the one gap `computeUpdatedText` doesn't cover (the Declaration line, cluster header comment, and reparenting-rule mutation) is handled by a new `src/sync/EntityDeletionSync.ts`. See `tasks.md`'s Phase 2 note for the full rationale.

### D4: Entity types in scope
- **Decision**: Classes, object properties, data properties, and annotation properties get the two-mode choice (per D1's per-type direct-subtype computation, using each type's `superClassIris`/`superPropertyIris`). Individuals are deleted directly with a single confirmation and no mode choice, since `OWLIndividual` (`OntologyModel.ts`) has no super/sub fields at all.
- **Rationale**: Matches spec Assumptions. Initial research undercounted this — `OWLAnnotationProperty extends OWLProperty` (`OntologyModel.ts:56`) and does carry `superPropertyIris`, and `AnnotationPropertyProvider.ts` already builds a `childrenOf` tree from it exactly like the object/data property providers do, so annotation properties must be treated the same as the other two property kinds, not excluded like individuals.

## Open questions
None — all `NEEDS CLARIFICATION` markers were resolved during `/speckit-specify` via documented Assumptions; no further research blockers for planning.
